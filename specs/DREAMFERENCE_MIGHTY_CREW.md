# Mighty Crew — a crew of coding-agent sessions on one codebase

**Status:** MVP specification, 2026-10-10, revised the same evening from the code and from the first day the crew ran. The binary `crew` exists in `src/` with every command of §5 (§12 lists the modules), and the offline suite of §9.6 (84 tests: 28 unit tests in the modules, 56 integration tests in `tests/`) passes; 0.2.0 (the same evening) added the decisions queue, `now`, `adopt`, `resource`, `handoff` and `up` (§4, §5), and CI runs it with `clippy` and `rustfmt` on every push. Measured on this machine the same evening: §9 items 1, 2, 5 and 6 hold in the suite; items 2 and 5 also against the live crew of four roles; item 3 for the delivered case (one live `crew msg`, §5); item 4 half-measured: the crew role's own session was resumed through `crew start crew` with `--continue` and started with the board in its context (the hook fired on `resume`); the reboot itself waits for the next one. The three shell scripts in `prototype/` are the behaviour this document was first written from, as run by hand on one machine that day (four sessions, four roles); the prototype launcher now starts every role in the bypass class with `--name <role>`, as §5 `start` requires. Facts about Claude Code below were checked against its documentation and `claude --help` for version 2.1.296 on 2026-10-10. Where this document is ahead of the code, the sentence says so with the date. §13 keeps the first day's lessons with the incidents they came from.

**Goal:** several coding-agent sessions work on one codebase at the same time, each with one role and one working tree of its own, and each starts knowing what the others did. The product does three things and nothing else: it starts a role in the right place, it keeps a shared board the roles write to and read from, and it carries messages between roles where the agent supports it.

**Builds on:**
- Claude Code's own facilities: `claude --continue` (a directory's conversation resumes), peer sessions on one machine with `ListAgents` and `SendMessage` (cross-session messaging), the `SessionStart` hook (text printed by a command becomes the session's first context), named sessions (`--name`), and `claude agents --json`, the read-only listing of live sessions (the form without `--json` needs a terminal; the product uses only the JSON form).
- git worktrees, which give every role a tree of its own on a shared repository.
- Mightling's rules for machines that hold a resident model: nothing is written into a repository that belongs to one user, and configuration lives under `~/.config`.

**Three things to know before reading further:**
1. **The MVP runs Claude Code only** (the owner's decision, 2026-10-10). `ling`, Mightling's agent, is a Codex build with no peer channel yet; it joins when it has one (§10). Everything in §5 except `crew msg` would already work for it, and the design keeps that door open.
2. **Every role runs with permission prompts bypassed** (the owner's decision, 2026-10-10), so a message from one role reaches another without a human approving it. Claude Code holds a message that crosses permission classes; one class across the crew removes the hold (§7). The owner accepts that each role then runs commands without asking.
3. **A crew has no lead.** Roles are peers. The product assigns no tasks, runs no orchestrator and never decides what a role does next; the user does, by talking to a role or by writing on the board. One role may be marked the **dispatcher**: the role the user talks through, which relays the user's words to the others (§2). It assigns nothing of its own and can grant nothing.

## 1. The problem

Running one agent session per concern on a codebase is the natural way to use more than one at once: one session on the product, one on the engine, one on operations. Done by hand, four things go wrong, each seen on 2026-10-10 before this document was written:

1. **Two writers in one checkout.** A session and a fork of it edited the same working tree; one's uncommitted changes sat under the other's test run and commit.
2. **No session knows what the others did.** A decision taken in one session (a default changed, a rule adopted) reached another only when the user retyped it.
3. **Messages held.** A session in one permission mode sent a line to a session in another; the receiver held it for approval, the approval never came, the line expired unread.
4. **Nothing survives a reboot.** Sessions, their background watchers and the knowledge of which directory each one owned were all in the user's head and terminal history.

Tools that run several agents in worktrees exist (claude-squad, dmux, MulmoTerminal, agent-of-empires and others); they solve the first and the fourth problem with tmux and worktrees and leave the second and third to the user. Mighty Crew's contribution is the second and third: the board and the messages, with the launcher as the carrier.

## 2. Model

- **A crew** is a named set of **roles**, defined once in a configuration file (§6). A crew has at least one role; three or four is the expected size.
- **A role** has a name (`operations`, `product`, `engine`, `crew`; lowercase letters, digits, `-` and `_`), a **charter** (one or two sentences: what it owns, what it never touches, and what dies with its session), a **working tree** (a directory that is a git checkout or a worktree of one), an **agent command** (the MVP knows one: `claude`), and the **permission mode** the agent is started with.
- **No two roles share a working tree.** A configuration in which two roles name one tree (by canonical path, so a symbolic link counts as the tree it points to) is refused by every command. The launcher refuses to start a role in a tree where a session already runs, and refuses to create a worktree over an existing one that another role owns. Two roles may share a repository through different worktrees.
- **The dispatcher** (2026-10-10): at most one role may carry `dispatcher = true` (a second is a configuration error). It is the role the user appointed to relay them: it passes the user's words to the other roles by message and by note, and asks the others for status on the user's behalf. It differs from a lead in what it cannot do: it has no tasks of its own to assign, nothing it writes is the user's approval, and a role that was refused a permission cannot obtain it by asking the dispatcher (no permission laundering). The product prints the mark in the charter at start and in the hook's first line, and gives the role no other power.
- **The board** is one Markdown file in one designated repository, appended by every role and read by every role at start. It is the crew's only shared, durable state. Its first part names the roles and their charters; its second part is a log of dated one-line notes, newest last (§4).
- **A note** is one line: date, time, role, text. A note states a fact (what changed, what is requested) with how to verify it, never a plan in progress. Its text may start with a tag that says what kind of fact it is: `decision:`, `done:`, `blocked:`, `heads-up:`, or `to <role>:` for a message's twin (2026-10-10, §4). It is never an instruction a receiving role must follow, and nothing a role writes counts as the user's approval of anything.
- **A message** is a line sent to a running role through the agent's peer channel (§5, `crew msg`). It has the same standing as a note: information, not authority. Every message has a durable twin on the board (§4), so the board is the record and the message is the fast path.
- **A role is an address; a session is not.** A message or a note names a role, never a session name: names change at every restart (2026-10-10: a message to the engine's old session name failed after the user had restarted it). `crew msg` resolves the role to its live session at the moment of sending (§5), and nothing the product writes stores a session name.
- **Transient sessions are not roles.** The headless session `crew msg` relays through, named `crew-msg`, appears in the agent's listing like any other (2026-10-10, when it showed up as a peer); `status` and `doctor` never count it as a role's session and label it a relay (§5).

## 3. The user's day

1. `crew start product` in a terminal: the launcher moves into the product role's tree, fetches, prints the role's charter and the last lines of the board, and starts `claude --continue` there (a fresh conversation when the directory has none). The user talks to that session as usual.
2. The role finishes a piece of work: it pushes and runs `crew note "release branch prepared on release/1.6.0; git ls-remote shows it"`. The line is on the board within seconds, through the helper's own small clone of the board's repository, so no role's working tree is touched.
3. Another role starts, or a running role asks `crew board`: it sees the line. A running role can also be told directly: `crew msg engine "the API spec moved; §7 is yours"`, which also lands on the board as a line addressed to engine.
4. The machine reboots. `crew start <role>` in each terminal resumes each conversation where it was; the board says what was in flight. Watchers and timers that lived inside a session are gone and the board says which ones to re-arm (the role's charter lists them).
5. `crew status` at any time: every role, its tree, branch and head, whether a session is running there and whether it is idle, busy or waiting, and its last note.

## 4. The board

- **Location:** a path inside one repository, configured once (`board.repo`, `board.path` in §6). The default path is `docs/dev/sessions.md`.
- **Shape:** a title (`# <crew>: the crew's board`), a short preamble (what the file is, how to append, that a note is information and not approval), a table of roles (`role | working tree | owns`), a `## Status` heading, then the notes, one per line, in the form `- YYYY-MM-DD HH:MM role: text`. The text may start with a tag, `decision:`, `done:`, `blocked:`, `heads-up:` or `to <role>:`, which is what a reader scans and what `crew board --tag` filters on (2026-10-10: notes had grown to hundreds of characters while `status` shows only their first words). A message's twin is a note of the sender whose text starts `to <role>:`. Two more sections may sit between the role table and `## Status` (0.2.0, 2026-10-10): `## Resources`, a table (`resource | owner | rules`) written by `crew resource`, and `## Decisions pending`, one block per open decision written by `crew ask`: `- d<N> · <date time> · <role>: <question>` followed by one task-list line per option, `  - [ ] <option>`, the recommended one marked `(recommended)`. The forge renders the boxes; a box ticked there (`[x]`), by hand from any device, is read by the next board write of any role, which removes the block and appends the choice as a `decision:` note signed `user`. Every write goes through one path (`Board::write`: fetch, change the sections, record ticked decisions, commit, push, three attempts), so notes, resources, asks and answers never disturb each other's sections. The first `crew note` creates the file with this header when it does not exist.
- **Writing:** only through `crew note` and `crew msg`, which clone the board's repository once into `~/.cache/mighty-crew/board/<repo>` (`$XDG_CACHE_HOME/mighty-crew/board/<repo>` when that variable is set; `<repo>` is the URL's last path component without `.git`) with blob filtering (a whole clone when the remote refuses the filter) and a sparse checkout of the one file, reset the clone to the remote branch, append the line, commit as the configured identity (git's own identity when none is configured) with the message `board: <role>` and push; on a rejected push they fetch again, append again on the fresh copy and retry, three attempts in all. A reachable remote whose branch does not exist yet is not an error: the first note creates the file with its header and the push creates the branch. The identity is set through git's author and committer variables for the one commit, so it wins over any identity git itself would pick. A hand edit of the file in a role's own tree is allowed but discouraged: it ties the note to that tree's next push.
- **The clock:** `crew note` stamps the machine's local date and time itself; a time typed into the text is text. `crew doctor` warns on a note dated before the one above it (§5).
- **Reading:** `crew board` prints the status section (the last 12 lines, `-n N` of them, or `--all`; `--for <role>` only the lines written by that role or addressed to it with `to <role>:`; `--tag <tag>` only the lines whose text starts with `<tag>:`, and `--decisions` is `--tag decision`); `crew start` prints the last 12 lines before the agent starts; a `SessionStart` hook installed by `crew install-hook` prints them into the session's context when a session starts in any role's tree, so an agent reads the board without being told. The hook is one entry in Claude Code's user `settings.json` (`~/.claude/settings.json`; the code assumes it moves with `CLAUDE_CONFIG_DIR`, which the documentation states for `projects/` only) that runs this binary as `crew hook`, a command not meant for hand use; its matcher is empty, so it fires on every `SessionStart`: `startup` for a new conversation, `resume` for `--continue`, and `compact` and `clear`, which puts the board back in context after a compaction (Claude Code adds the hook's plain stdout to the session's context). Its first line names the role, its charter, the dispatcher mark when set, the board's file and repository and how to append; it then says that a message to another role goes through `crew msg`, which writes the message's twin, because a `SendMessage` the agent sends on its own leaves no record (2026-10-10, §7). The hook gives the board's refresh 20 seconds, the prototype's `timeout 20`; it then prints the last fetched copy and says so when the refresh failed, and prints nothing and exits 0 outside a role's tree or without a configuration, so a session never waits on the network.
- **Never rewritten:** a role appends its own lines and never edits another's. The role table changes only when the configuration changes, through `crew board --sync-roles`, which rewrites everything above `## Status` from the configuration and keeps every note (commit message `board: roles`).
- **Why a file in git and not a service:** the crew's machines may be air-gapped from everything but their own git remote; a file in the repository the roles already push to needs no new service, survives reboots, is visible on the forge, and has a history.

## 5. The command line

```
crew start <role> [--new] [--create]   start (or resume) the role's agent in its tree
crew open  <role>                      the same, in a new terminal window (needs a display)
crew board [-n N] [--all] [--for ROLE] print the board's status lines (default: the last 12)
crew board --sync-roles | --cached     rewrite the role table from the configuration; print without fetching
crew board --tag TAG | --decisions     the lines whose text starts with `TAG:`; `--decisions` is `--tag decision`
crew board --pending                   the decisions still waiting for the user
crew ask "<question>" --options a,b,c  post a decision for the user on the board [--recommend X] [--as ROLE]
crew answer <id> <option>              record the user's choice as a `decision:` note
crew now ["<doing>"]                   what a role is doing right now (this machine only); no text: every role's line
crew adopt <role> [--mode M]           record the class of a session started by hand, so doctor stops asking for a restart
crew resource [<name> "<rules>"]       declare a shared resource and its rules on the board; no arguments: list them
crew handoff <role> <path>             copy a file or directory into the neutral hand-off folder and note it
crew up [--new]                        from a clone to a live crew: create missing worktrees, open every role
crew note  [--as ROLE] "<text>"        append a dated line as the role whose tree you are in
crew msg   <role> "<text>"             send a line to that role's running session, and to the board
crew status                            roles, trees, branches, heads, sessions, last notes
crew doctor                            check the configuration, the trees, the sessions, the board, the hook
crew install-hook | remove-hook        the SessionStart hook that prints the board, and the /crew skill
crew init [--force]                    write a configuration from the current repository
```

- **`start`.** Resolves the role. The tree must exist and be a git checkout, and must not be another role's. When the tree is missing and the role has `worktree_of` and `branch`, `start` prints the `git worktree add` it would run and refuses; `--create` runs it (the branch is created from the repository's `origin/HEAD` when it does not exist yet, after a fetch; from the repository's `HEAD` when the remote's default branch is unknown). Then it refuses when the agent's listing shows a live session whose working directory is the tree, naming that session: one session per tree is what the crew exists for (two sessions sat on one tree for forty minutes on 2026-10-10); when the listing itself fails, `start` goes on without this check. Then, when the tree is clean and has a remote, it fetches (30 seconds; a failed fetch is reported and the start goes on offline) and fast-forwards a plain checkout (a worktree, whose `.git` is a file, keeps its branch where it is). It prints the charter (`== <role> role of crew <crew> in <tree> (<branch> at <head>)`, then `owns:`), the board's last 12 lines (a 20-second refresh, the last copy when the remote does not answer), records the tree and permission mode it is about to use under `~/.cache/mighty-crew/started/<role>` for `doctor`, and replaces itself with the agent command, run in the tree with `--name <role>` and `--permission-mode <mode>`. `--continue` is added when the directory has a conversation and `--new` was not given; otherwise the conversation is fresh and `start` says so. A directory has a conversation when Claude Code's `projects/<name>/` holds a `.jsonl` transcript, where `<name>` is the tree's absolute path with every character outside letters and digits replaced by `-` (`/home/u/w/.claude/worktrees/product` becomes `-home-u-w--claude-worktrees-product`), under `~/.claude` or `CLAUDE_CONFIG_DIR`. Claude Code truncates and hashes the name of a path over 200 characters; such a tree is not recognised and `start` starts fresh there, a known limit.
- **`open`.** `start` in a new terminal window, using the first of the terminals the configuration names (`terminal.commands`) or the ones the machine has (`x-terminal-emulator`, `gnome-terminal`, `konsole`, `xterm`), run with this binary's absolute path. Without a display (`DISPLAY` and `WAYLAND_DISPLAY` both unset) it prints the `start` command to run instead and exits 0.
- **`board`.** Refreshes the clone (60 seconds) and prints the status lines; `--cached` prints the last fetched copy without a fetch; a board file that does not exist yet is reported, not an error. `--for <role>` keeps the lines written by that role and the lines addressed to it; `--tag <tag>` (2026-10-10) keeps the lines whose text starts with `<tag>:`, and `--decisions` is `--tag decision`. `--sync-roles` rewrites the role table (§4).
- **`note`.** The role is the one whose tree contains the current directory, the deepest tree when trees nest (a worktree under its repository's checkout belongs to the worktree's role); `--as <role>` overrides. The text is one line; a longer text is folded onto one line; an empty text is refused. The line is printed back as written.
- **`msg`.** Finds the role's running session through the agent's own listing (a live row whose working directory is the role's tree, an interactive one first; refused with one line, `no session is running in <tree>`, when there is none, naming the `crew start` to run). The role is resolved to its live session at the moment of sending and the session's name is used for that send only; nothing stores it, because session names change at every restart (2026-10-10: a message to the engine's old session name failed after the user had restarted it). It then sends the text, folded onto one line, through the agent's own messaging, addressed to the session's name. The sender identifies with the permission mode of the role whose tree the command runs in, or the crew's when run elsewhere. Before sending, `msg` appends the same text to the board as a note of the sending role, `to <role>: <text>`, so a message that is held, expired or dropped is still on the record; a message that cannot be written to the board is not sent, and a role does not message itself. **What `msg` can report.** Claude Code reports a message as accepted into the receiving session's inbox, held for that session's user, or refused; the receiving agent reads an accepted message between tool calls of its current turn or at the start of its next, and `msg` cannot see that. So `delivered` means "in the inbox", exit 0; `held` (the roles are in different classes, §7) exits 1 and is never retried; `refused` exits 1. Receivers preview only the first line of a message, so the one line `msg` sends must be short and stand on its own: `msg` refuses a text over 300 characters and says to put it on the board or in a file the message names (the figure is this document's pick, 2026-10-10). **The carrier.** What Claude Code's documentation states (read 2026-10-10): there is no command, flag or SDK call that posts a message into a running session from outside one; each session binds an inbox socket meant for scripts, of which only the opening auth line is documented, not the line that carries a message; and a message's delivery or hold depends on the permission class the sender identifies with, for which the documentation gives an outside script no way to assert one. So `msg` runs the agent itself headless (`claude -p`) in the sender's permission class, named `crew-msg`, on the model `agent.msg_model` (§6; the default `haiku`, since one `SendMessage` call needs no more), with `SendMessage` and `ListAgents` pre-approved through `--allowedTools`, at most four turns, without persisting its conversation, asked to send the text verbatim as data, then to list the sessions once so a delivery notice can arrive, and to end with one word, `DELIVERED`, `HELD` or `REFUSED`, followed by the agent's own result text, which `msg` prints; a report without the word counts as refused. The documentation does not say whether `SendMessage` prompts in a headless session, so the allow-list is the documented way to pre-approve it. The cost is one model turn per message, with a three-minute limit; the board stays the free path. Measured on 2026-10-10 at 16:00, one message from the crew role to the operations role, both in the bypass class, on `haiku`: 11 seconds wall-clock from the command to its exit, the twin on the board, the relay's report `DELIVERED: SendMessage to dgxcoder-93 succeeded and is in its inbox, not yet read`. A direct socket carrier replaces this when the message line is documented (§10). Only for agents with a peer channel (the MVP: Claude Code).
- **`ask`, `answer`, `board --pending`** (0.2.0, 2026-10-10; the decisions queue of the first day, §13). `ask` takes one question and at least two options (`--options a,b,c`, repeatable), an optional `--recommend`, and posts the block under `## Decisions pending` with the next free id (`d<N>`, one past the highest id pending or decided, so ids never repeat), signed by the role whose tree the command runs in or `user`; it prints the id, the options and, for an http(s) repository, the forge's link to the section. `answer <id> <option>` matches the option case-insensitively, removes the block and appends `decision: <id> <option>; <question> (asked by <role> at <when>)` as a note of the answering role or `user`; a wrong id lists the open ones, a wrong option lists the options, and an id answered on the forge in the meantime is refused with a pointer to `--decisions`. `board --pending` lists the open decisions, marks one ticked on the forge as answered and not yet recorded, and names the link. The hook's text and `status` state the number of decisions waiting. Measured in the suite: ask, answer, a tick by hand on the remote recorded at the next unrelated note, ids past a decided one.
- **`now`** (0.2.0). `crew now "<doing>"` writes the line with the clock under `~/.cache/mighty-crew/now/<role>` on this machine, outside the board; `crew now` prints every role's line. `status` shows it in a `now` column with its age; a fresh `now` line counts as activity for `doctor`'s quiet rule, and the line is the role's claim on the task (§7).
- **`adopt`** (0.2.0). `crew adopt <role> [--mode M]` writes the start record for a session that runs in the role's tree but was started by hand (refused when none runs), so `doctor` compares the recorded mode with the configuration instead of asking for a restart; a mode outside the crew's class is recorded and warned about.
- **`resource`** (0.2.0). `crew resource <name> "<rules>"` adds or updates one row of the `## Resources` table with the current role as owner; unchanged rules are reported, not committed; `crew resource` lists the table; `status` prints it in one line.
- **`handoff`** (0.2.0). `crew handoff <role> <path>` copies the file or directory into `~/.cache/mighty-crew/handoff/<from>/<to>/<name>/` (refused when that exists), appends `to <role>: handoff <name> at <dir> (<N> files)` as a note of the sending role, and prints the scrub reminder, with the count of copied text files that mention a `/tmp/` path.
- **`up`** (0.2.0; the growth document's §8). For every role in order: the tree is created when missing and configured (as `start --create`), a role whose tree is missing otherwise is reported and skipped, a role with a live session is listed as already running. The roles left are opened at once: with `tmux` on `PATH`, one session `crew.<name>` with one window per role running `<this binary> start <role> [--new]`, then `tmux attach` (or `switch-client` inside tmux); an existing session is attached, not rebuilt; without tmux but with a display, one terminal window per role through `open`; with neither, the start lines to run. `up` opens sessions and assigns nothing, and there is no `crew down`.
- **`status`.** Refreshes the board (60 seconds; the last copy when the remote does not answer) and lists the agent's sessions once per agent command, then prints one aligned row per role: tree, branch (`(detached)`, or `(missing)` for a tree that does not exist), head (short hash and the first words of the subject), session (its state and name, or `not running`), and the role's last note on the board (its time and first words, or `-`). The listing is `claude agents --json`: one row per live session with `cwd`, `kind` (`interactive` or `background`), `name`, `sessionId` and `startedAt`; an interactive row carries `pid` and `status` (`busy`, `waiting` or `idle`; `waitingFor` says what for), a background row carries `state` instead (`working`, `blocked`, `done`, `failed`, `stopped`). Measured on this machine on 2026-10-10 with four interactive and five background sessions: every interactive row had `status` and `pid`, every background row `state`. Rows in a finished state (`done`, `failed`, `stopped`) are dropped; a role is running when a remaining row's `cwd` is its tree, and the state printed is that row's `status` (with what it waits for), else its `state`, else `running`. A row named `crew-msg` is the relay `msg` runs (§5) and never counts as a role's session (2026-10-10). Two more columns per role (2026-10-10): the commits on the branch's upstream since the role's last note (`-` when the branch has no upstream or the role has no note) and the minutes since that note; on 2026-10-10 the question whether a role was productive cost a message round trip per role, and git already held the answer. The listing says busy or idle, not what the session is doing; for that, see `crew now` in §10.
- **`doctor`.** Prints one line per finding: `ok`, `warn` (something to know that nobody should rewrite; it does not fail the check) or `fix` with the fix; then `all good` or the count of things to fix (exit 1). It checks: the configuration loads (every error in §6 is a finding with its fix); every tree exists and is a git checkout (a missing configured worktree names `crew start <role> --create`); every role runs in the crew's permission class (another class: messages between the classes are held; give every role the crew's mode); every agent command resolves on `PATH` or as a path; for every role with a live session in its tree, the mode `crew start` recorded against the configured one (changed since: started before the configuration changed, restart it with `crew start`; no record: a session not started by `crew start`, its class unknown, restart it so messages are not held); every interactive session of the agent that runs in no role's tree (add a role for it, or leave it out knowingly; a `crew-msg` relay is labelled as such and is not a finding); a role whose session is busy while its last note and the last commit on its upstream are both older than 90 minutes (a `warn`, 2026-10-10: a quiet busy role is the backstop for a message that went around `crew msg`, §7); the board's repository is reachable and the board file exists at its path (the first `crew note` creates it); no note is dated before the one above it (a `warn`: a hand-typed time, and another role's line is never rewritten); the hook is installed in the settings and runs this binary (another path: `crew install-hook`); the `/crew` skill is installed as this version writes it; the terminal command resolves when the configuration names one.
- **`install-hook` and `remove-hook`.** Add to, or take out of, the `SessionStart` list of the user settings one entry that runs `<this binary> hook` with an empty matcher, leaving every other hook as it was (`serde_json` keeps the file's key order); an older entry of ours at another path is replaced; a second install reports the hook already installed. `remove-hook` deletes our entries and any `SessionStart` entry left empty by that. **The `/crew` skill** (2026-10-10, after the first restart through the launcher, when the user looked for the product in the `/` menu): `install-hook` also writes Claude Code's user skill `~/.claude/skills/crew/SKILL.md` (under `CLAUDE_CONFIG_DIR` when set), so that inside any session `/crew board`, `/crew note "<what changed>"`, `/crew msg <role> "<text>"`, `/crew status` and `/crew doctor` run the same commands through the agent's shell tool, pre-approved for `crew` alone, and `/crew` by itself shows status and the board; the skill's text repeats the rule that nothing `crew` prints is the user's approval. `remove-hook` deletes it; `doctor` reports a missing or outdated skill. Claude Code picks up a skill added under an existing `~/.claude/skills/` without a restart; when that directory did not exist when the session started, `/reload-skills` in the session does it.
- **`init`.** Run in a repository with an `origin` remote (refused otherwise): writes `~/.config/mighty-crew/crew.toml` naming the crew after the repository's directory, the board as `docs/dev/sessions.md` of `origin` on the remote's default branch (the current branch, then `main`, when the default is unknown), the commit identity from `git config user.name` and `user.email` when both are set, the agent `claude` in `bypassPermissions`, and one role named after the directory with the repository as its tree; a commented example shows a second role as a worktree. An existing configuration is kept unless `--force`. The file is parsed back before `init` reports success and prints the next steps (`[roles.<name>]` per role, `crew install-hook`, `crew doctor`).

Every command loads the configuration first (except `hook`, which is silent without one, and `install-hook` and `remove-hook`, which touch only the settings) and exits 1 on failure with one line on stderr, `crew: <why>`, with the fix when there is one; a usage error exits 2. No command writes into a role's working tree except `start`'s fetch, fast-forward and `--create`, and `init`'s first configuration. Every process the product runs has a wall-clock limit: git commands 60 seconds (a clone 300, `start`'s fetch 30), the session listing 30, the hook's refresh 20, the headless send 180; a process that overruns is killed and the command fails with one line, so no command hangs on a remote that does not answer. The runner reads both output streams on threads of their own and counts the limit from the spawn, so an open pipe does not stop the clock.

## 6. Configuration

`~/.config/mighty-crew/crew.toml`, written by `crew init` and edited by hand; never inside a repository, because it names machine-local paths and the user's own choices (Mightling's rule). On Windows (2026-10-10) the same paths hang off `%USERPROFILE%` (`HOME` when set), a command name resolves through `PATHEXT` (`claude.cmd`, `crew.exe`), and `start` runs the agent as a child process and exits with its code instead of replacing itself. Prebuilt binaries for Linux (x86_64 and aarch64, static musl), macOS (Apple silicon and Intel) and Windows (x86_64) are built by the release workflow on every `v*` tag and attached to the release with a SHA-256 beside each; `install.sh` (Linux, macOS) and `install.ps1` (Windows) in the repository root install the latest into `~/.local/bin` or `%LOCALAPPDATA%\Programs\crew`, checking the sum. `$XDG_CONFIG_HOME` replaces `~/.config` when set; a `MIGHTY_CREW_CONFIG` variable overrides the whole path. The product reads four more variables: `HOME` (required, for `~`), `XDG_CACHE_HOME` (the board clone's and the start records' base), `CLAUDE_CONFIG_DIR` (where Claude Code keeps its `projects/`, for the conversations, and, the code assumes, its `settings.json`, for the hook; `~/.claude` otherwise) and `PATH` (to resolve the agent and terminal commands); and `DISPLAY` and `WAYLAND_DISPLAY` in `open`.

```toml
[crew]
name = "mightling"

[board]
repo = "https://github.com/dreamference/mightling.git"
path = "docs/dev/sessions.md"                        # default
branch = "main"                                      # default
identity = { name = "dgxcoder", email = "dgxcoder@dreamference.ai" }   # git's own identity when absent

[agent]
command = "claude"                                   # default; a name on PATH or a path, `~` allowed
permission_mode = "bypassPermissions"                # default; every role, the owner's decision
msg_model = "haiku"                                  # default; the model of the headless session `msg` relays through (§5)

[terminal]
commands = ["kitty"]                                 # for `open`; the machine's own terminals when absent

[roles.operations]
tree = "~/PycharmProjects/dgxcoder"
owns = "the benchmark nights and their watcher, the model server and gate, installs, releases, the machines"
dispatcher = true                                    # the role that relays the user (§2); at most one

[roles.product]
tree = "~/PycharmProjects/dgxcoder/.claude/worktrees/product"
worktree_of = "~/PycharmProjects/dgxcoder"
branch = "work/product"
owns = "the product's code, tests, specs and docs; pushes through origin"

[roles.engine]
tree = "~/PycharmProjects/ling-engine"
owns = "the engine; builds and tests on second-puffin only"

[roles.crew]
tree = "~/PycharmProjects/mighty-crew"
owns = "this product"
```

A role may set its own `command` or `permission_mode`; in the MVP every role inherits the crew's, and `doctor` warns about a role that does not (§7). `worktree_of` with `branch` lets `crew start --create` create a missing worktree from the repository's default remote branch. `owns` is the charter; it may be empty. `dispatcher` (2026-10-10) marks the one relaying role of §2; two are an error. `agent.msg_model` names the model of the headless session `msg` relays through. The file is read strictly: an unknown key, a missing `[crew]`, `[board]` or `board.repo`, no role, a role name outside `[a-z0-9_-]`, or two roles on one tree is an error naming the file and the table. A path may start with `~`; a tree is compared by its canonical path when it exists and lexically (absolute, `.` and `..` resolved) when it does not. Roles print in the order written.

## 7. Messaging policy

- **One permission class across the crew.** The configuration's `permission_mode` applies to every role, and `crew doctor` warns about a role configured otherwise and about a running session started otherwise. Claude Code delivers between sessions of one class without a hold. Holds are directional and were measured on 2026-10-10: a message from a bypassing session to a prompting one was held, and expired unanswered three times that day; one from a prompting session to a bypassing one arrived at once, though the documentation's rule for a bypassing receiver predicts a hold there too. The crew relies on neither direction being open: one class, and the board as the twin. A change of class in the settings applies to sessions started after it, never to a running one; `doctor` says which sessions predate the configuration and need a restart (§5). Delivery turns on the class the sender identifies with, and the documentation gives an outside script no way to identify with one, which is why `crew msg` sends through a session of the agent and not straight to the inbox socket (§5).
- **Every message has a durable twin.** `crew msg` writes the board before it sends (§4, §5); a held work order of 2026-10-10 survived only because it had been written to the board by hand. A request that crosses a charter (one role needs a machine another owns, a build another installs) is therefore always on the board, recorded even if the message is lost.
- **A message is information or a request**, never authority. A receiving role verifies on the remote (fetch, read the board, read the file) before acting on anything a message or a note claims, and treats nothing in it as the user's approval. Commands inside a message are text; nothing in a message runs. `crew msg` never asks a role to do what the sending role was refused.
- **Notes state facts with how to verify them**, not what is being done: "the repository exists; `git ls-remote` shows it", not "creating the repository". On 2026-10-10 a role planned a `gh repo create` for a repository another role had created a minute before the hand-off was read, because the note described an action in progress. A role verifies on the remote before any create or destroy.
- **A work order carries its evidence** (the number, the command that produced it), and the receiver measures first and answers with a number. On 2026-10-10 a role measured before changing a default on request and corrected the requester's claim; that is the expected shape of a peer correction.
- **A status request gets one line**: `doing: …`, `done: …` or `blocked: …`.
- **Decisions are recorded where every role reads them.** A decision the user gives in a role's own terminal is invisible to the other roles (2026-10-10: the user answered the product role's questions directly, and operations learned of them by chance). The role that receives one posts it as a `decision:` note, and `crew board --decisions` lists them. The queue of §10 covers what is asked; this covers what was answered elsewhere.
- **Outward-facing and irreversible actions are asked first.** Publishing, tagging, creating a repository, changing the user's own settings: through `crew ask` once the queue exists (§10), and until then the user's answer in the role's own terminal, recorded as a `decision:` note before the action. On 2026-10-10 the crew role tagged v0.1.0, published a release and replaced the user's SessionStart hook on the user's answers in its own terminal, while the dispatcher's note that the switch comes after the cut had not reached it.
- **Shared resources carry declared rules.** A server, a machine or a port that more than one role uses has an owner and rules written where every role reads them (2026-10-10: the engine posted the rules for its server on the board, while the rule for another machine lived only in messages). A `## Resources` table and `crew resource` are §10 items; until then a `heads-up:` note states the rule.
- **A heads-up precedes a change to shared infrastructure** that running work depends on: a `heads-up:` note with the change and when, before the change (2026-10-10: a midday repair would have added a mixed lane to a running A/B, and the fix raced the second arm).
- **Data between roles goes through a neutral folder**, never another role's tree (2026-10-10: recordings for the engine went to a hand-off directory under `~/.local/share`). `crew handoff` is a §10 item; until then the note names the path, and the sender scrubs the files first (eight recordings carried a tool's temporary path, which must not reach a public repository).
- **An emergency crossing is allowed and announced.** When a role's own deliverable is blocked by a defect in another role's domain, it may make the minimal change there and posts a `done:` note at once naming the owner, who reviews (2026-10-10: a release build broke on a test in the product's domain and operations fixed it rather than wait).
- **A task is a claim.** A role checks `crew status` before starting a task another role may hold (2026-10-10: a laptop test ran twice, once from a fork the user started and once from the product role on a relayed order). `crew now` (§10) is also a claim.
- **The agent's own channel cannot be intercepted.** Agents have `SendMessage` and use it on their own, so the board-twin rule holds only for what goes through `crew msg`. The hook's text tells every session so at start (§4), and `doctor`'s warning on a quiet busy role is the backstop (§5).
- **A restart is how a settings change propagates.** An inbound setting or a new launch mode reaches only sessions started after it; `crew start <role>` with `--continue` keeps the conversation under the new name and class (2026-10-10: the crew role's own restart). `crew restart` (§10) says so: the conversation survives, the address changes.
- **A role's background agents** (subagents, forks) never write in the role's tree: they work read-only or in a throwaway worktree of their own. On 2026-10-10 a fork collided with its parent in one tree.

## 8. Reboot and recovery

- Each role's conversation is the agent's own, keyed by directory; `crew start <role>` resumes it.
- The board's clone under `~/.cache` is rebuilt from the remote when missing; the start records under `~/.cache/mighty-crew/started/` are rewritten at the next `crew start`.
- A role's charter names what dies with its session (timers, watchers, held background work); `crew start` prints the charter so the resumed session re-arms them. The product keeps no daemon and starts none: anything that must outlive a session belongs to the operating system's timers, configured by the role that owns it.

## 9. Acceptance

The MVP is done when all of these hold on one Linux machine with Claude Code installed:

1. `crew init` in a repository, then `crew start` for each of three roles from one command each, gives three sessions in three distinct trees; a fourth `crew start` naming a tree where a session already runs is refused with one line, and a configuration giving two roles one tree is refused by every command.
2. A `crew note` written in one role is printed at the next `crew start` of each other role and by `crew board` in all of them, within a minute, with the correct role name and time.
3. With every role in one permission class, `crew msg` from one role is read by the other's agent in its next turn and its twin is on the board; `crew msg` reports the hold when a role was started in another class, and the twin is on the board all the same.
4. After the machine reboots, `crew start <role>` for each role resumes its previous conversation and prints the board.
5. `crew status` shows each role's tree, branch, head, running state and last note; `crew doctor` reports a missing tree, a missing board file, a wrong hook path, a mismatched permission class (configured, or recorded at start) and a session in no role's tree, each with its fix, and labels a `crew-msg` relay instead of counting it.
6. The suite runs offline: the board is tested against a local bare repository, the agent command against a stub, and no test reaches the network or the user's home: `HOME`, `XDG_CONFIG_HOME`, `XDG_CACHE_HOME`, `CLAUDE_CONFIG_DIR` and `MIGHTY_CREW_CONFIG` point into the test's own directory (§6 names every variable the product reads).

## 10. Non-goals and later

- **Non-goals of the MVP:** no orchestrator, no task queue or assignment, no shared working tree, no polling loop that costs a model turn, no service or daemon, no web view (`claude agents` is the view), no agent other than Claude Code.
- **Later, in order** (the dated items come from the first day the crew ran, 2026-10-10):
  1. `ling` as an agent (board, notes and launcher work today; `msg` when the launcher gains a peer channel).
  2. Built in 0.2.0 (§5): `crew now "<doing>"` (2026-10-10): a role states what it is doing in `~/.cache/mighty-crew/now/<role>`, distinct from a hand-off note, and `crew status` shows it at once; a status question then costs no message round trip, and the line is the role's claim on the task (§7).
  3. `crew wait <role>` (2026-10-10): a one-shot subscription to the role's idle notice, through the agent's own `notify_when_idle`, so the user hears when a role finishes without asking it.
  4. `crew restart <role>` (2026-10-10): after a configuration change, waits for the role's idle notice, then tells the user the role can be restarted in the new class, that the conversation survives and that the address changes (§7); the product never kills a session.
  5. `crew fork <role>` (2026-10-10): a background copy of a role's session in a throwaway worktree, so forks never share the parent's tree.
  6. `crew add-role <name>` (2026-10-10): appends the role to the configuration and the board's table, with a `joined` note.
  7. `crew init` offering to link each role's agent memory to one crew memory (2026-10-10): agent memory is per directory, so each role remembers alone; linking is the Claude Code adapter's job and touches an agent-internal path, so it stays optional.
  8. `msg` straight over the receiving session's inbox socket, without a model turn, once Claude Code documents the message line (§5).
  9. A tmux layout for `open` on machines without a display; a board view that groups notes by role; packaging as a release binary and, for Mightling nodes, installation by `ling-admin`.
  10. Built in 0.2.0 (§4, §5): `crew ask "<question>" --options a,b,c` and `crew answer <id> <option>` (2026-10-10): a decisions queue on the board. On the first day the user answered about twenty-five questions in six batches, each relayed by hand through one session. `ask` posts the decision to a third section of the board, `## Decisions pending` (asked by which role, when, the options, the recommended one); `crew board --pending` lists what is open; the user reads the queue when they want and `answer` records the choice as a note every role sees at its next start. A pending decision is visible to every role, so two roles never ask the same thing, and an answer is a durable fact on the board, not a message that can be held. Outward-facing and irreversible actions go through it first (§7).
  11. Built in 0.2.0 (§5): `crew resource <name> "<rule>"` (2026-10-10): a `## Resources` table on the board (resource, owner, rules), shown by `status`, so the rules for a shared server or machine live where every role reads them (§7).
  12. Built in 0.2.0 (§5): `crew handoff <role> <path>` (2026-10-10): copies a file or directory into `~/.cache/mighty-crew/handoff/<from>/<to>/<name>/`, posts a note naming it, and prints a reminder to scrub temporary paths before anything reaches a public repository (§7).
  13. How the product spreads beyond one machine and one crew is proposed in [DREAMFERENCE_MIGHTY_CREW_GROWTH.md](./DREAMFERENCE_MIGHTY_CREW_GROWTH.md), each item dated with the line that says it is done.
